# 0008. 失败降级与幂等运行

- 状态：已接受
- 日期：2026-11-14
- 关联：[0004](0004-evidence-gates.md)、[0007](0007-deepseek-api-model-tiering.md)、[0012](0012-output-contract.md)

## 背景

逐条主张的流水线会经历解析、检索、多次模型调用和校验；任何一环都可能失败。关键在于：失败时结论应该倒向哪边？如果放宽校验或中止整篇，都会破坏"有据才支持"的承诺。

## 决策

1. **失败一律倒向存疑**：
   - 检索无结果 → 直接存疑，不调用 judge（省钱且不可能产生假支持）。
   - 输出不合 schema → 重试一次 → 仍失败存疑。
   - 引用不是逐字子串，或不属于所检文档 → 存疑。
   - verifier 判证据不足或与 judge 不一致 → 存疑。
   - 版本不匹配、需要跨文档综合 → 存疑。
2. **单条失败不中止整篇**：逐条记录失败原因，继续处理其他主张；整篇解析失败或配置错误才以退出码 3 中止。
3. **重试与限流**：429/5xx/超时按指数退避重试，最多 3 次；尊重并发上限；请求 10 分钟未开始推理时服务端会断开，客户端需处理。
4. **幂等运行**：缓存键 = `SHA256(文章)` + `KB manifest 哈希` + 模型配置 + 提示词版本 + 代码版本。命中缓存时直接复用结论；`--no-cache` 强制重跑。
5. **可审计**：每次运行写入 `trace.jsonl`，记录检索结果、闸门结果、模型用量和失败原因；不记录 API Key。

## 备选方案

- **异常即中止整篇**：避免半成品，但会让一条坏主张毁掉整篇文章的核验；排除。
- **放宽校验，尽量给结论**：直接制造假支持；排除。
- **失败时回退到模型内部知识**：违背产品前提；排除。

## 后果

- KB 覆盖不足或提示词不稳定时，会出现大量「存疑」；这是可见、可解释的失败，而不是静默的错误支持。
- 缓存让评测可复现、重跑不重复付费；但缓存键必须包含提示词版本和代码版本，否则结论会悄悄漂移。
- trace 可能包含文章和证据片段；敏感场景需配合 `--no-store-article`（[0011](0011-privacy-provider-boundary.md)）。
