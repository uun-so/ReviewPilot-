# 0009. KB manifest、版本与冲突策略

- 状态：已接受
- 日期：2026-11-14
- 关联：[0001](0001-closed-world-kb.md)、[0002](0002-verdict-taxonomy.md)、[0005](0005-single-hop-mvp.md)

## 背景

技术文档有时效性：同一个 API 在 v1 和 v2 中默认值可能不同。如果知识库同时收录多个版本，模型很容易用最新文档回答旧版本主张，得出"有据但错误"的结论。另一方面，KB 内部可能自相矛盾；自动选边等于替模型猜。

## 决策

1. manifest 必填 `name`、`version`、`effective_date`、`sensitivity`；每个 source 记录 `path`、`title`、`format`、`url`、`retrieved_at`、可选的 `version` 和 `sha256`。
2. 索引与 manifest 哈希绑定；重建索引是显式命令。运行记录所用 manifest 的 `name`、`version`、哈希。
3. **版本匹配优先**：主张中出现版本号/日期时，只有 manifest 中 `version` 匹配的 source 才能作为判定证据；没有匹配 → 存疑，原因 `no_matching_version`。禁止用最新文档回答旧版本主张。版本提取只把显式 `vX.Y` 或带“版本/version”上下文的数字当作文档版本；`HTTP/1.1`、`path/2.0` 等协议或路径数字不参与版本门控，反引号内的代码标识符先剔除。
4. **冲突处理**：同一主张存在通过闸门的支持证据和反证证据时，结论为「冲突」，双方证据都列出。若冲突跨版本，标注 `cross_version_conflict`，不自动选边。
5. **不自动取最新**：最新文档不是"更正确"的同义词；版本差异必须由作者判断。
6. 同一文档内部的矛盾同样按冲突处理；不因为"同一来源"就取其一。

## 备选方案

- **忽略版本，用任意相关文档**：会把版本错配误判为支持；排除。
- **自动取最新版本**：会把"文档写错了"误判成"文章写错了"；排除。
- **一律存疑**：能避免错误，但丢失最有价值的冲突信号；排除。

## 后果

- manifest 的版本标注成为知识库质量的一部分；缺失版本会导致相关主张更容易存疑。
- 冲突结论需要人工判断，报告必须清楚展示版本、日期和双方引用。
- 评测集需要包含版本错配和 KB 内部矛盾的样本，否则无法验证这条策略。
